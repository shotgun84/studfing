Lehman’s Laws
Meir M. Lehman, a pioneer in software engineering, observed how large software systems 
behave over time. 
These are scientific laws — they describe how things behave, not how they should be.
Two Key Laws:
Law of Increasing Complexity: 
Every time we make changes to the program, it becomes a bit more complicated, 
unless we clean it up.
Law of Continuing Change: 
If a program is useful, people will want it to do more over time. 
So, it needs to keep changing to stay useful.

Key Modularity Principles
How do we manage this growing complexity? One of the most effective 
tools we have is modular design.
High Cohesion: Each module does one clear task.
Low Coupling: Modules don’t overly depend on each other.
Information Hiding: A module hides its internal details and exposes only 
what others need.
Code Reuse: Shared functionality should be in one place and reused.

Coupling – Interdependence Between Modules
e.g. In a date-handling module:
isLeapYear(y) determine whether the year is a leap year.
calcDaysInMonth(m,y) calculate the number of days in a given month and year
To correctly compute the days in February, calcDaysInMonth(m,y) must determine 
whether the year is a leap year.
calcDaysInMonth(m,y) calls isLeapYear(y) to ﬁnd out.
Thus, calcDaysInMonth(m,y) depends on isLeapYear(y)
This kind of dependency is called coupling.
Note : Coupling can result from both interactions between modules and the way parameters 
are used.

===== PAGE BREAK =====

Degree of Coupling
Coupling varies in strength:
Loose coupling (preferred)
Tight coupling (problematic)
We prefer it to be as loose as possible:
The loosest coupling is not no coupling.
Some coupling is essential for functionality.
Problems with tight coupling:
Changes in one module strongly affect another.
Developers must understand both modules simultaneously.
Aim for loose coupling to improve modularity, maintainability, and scalability.

Things to consider : Calls
A function call (also known as an invocation) is the most direct and visible form of coupling.
What happens during a call:
1. when calcDaysInMonth(m,y) calls isLeapYear(y):
2. calcDaysInMonth pauses execution.
3. The value y(year) is passed to isLeapYear(y).
4. isLeapYear performs its logic and return a result.
5. The result is returned back to calcDaysInMonth(m,y).
6. calcDaysInMonth resumes, receiving and using the result in its own computation.
The caller depends on the callee’s interface and behaviour.
Calls commonly use parameter passing and return values.

Things to consider: Relatedness of Tasks
Even when a function does multiple tasks, the degree of cohesion depends on how related those tasks are.
Completely unrelated 
Tasks have no logical connection. Should be split entirely.
extremely low (essentially zero) cohesion.
Superficially related (e.g., by name)
Grouped under a broad label, but not functionally coherent.
low cohesion
Related by time 
Tasks must happen together or in sequence but are distinct.
Moderate Cohesion
Related by data
Tasks use or transform the same data. 
Often tightly coupled.
Higher Cohesion

Things to consider: Different Data
If different parts of a method or function operate on different sets of data, it likely suffers from low cohesion.
Why It's Problematic
Indicates the function is doing unrelated or loosely related tasks.
Harder to understand, test, and reuse.
Often a sign the function should be split up.

Reuse and Coupling
Reuse is desirable…
But reuse can increase coupling, because multiple parts now depend on the same component.
Reuse and coupling are not opposites, they must be carefully balanced, not blindly optimized.
Sensible Design
Reuse only when tasks are truly the same.
Don’t “force” reuse for things that aren’t actually shared responsibilities.
Avoid introducing tight dependencies just for the sake of reuse.
If You’re Not Careful
introduce unnecessary coupling.
mistake similar-looking code for actual duplication.
reduce cohesion by forcing unrelated code to share logic.

Summary
Modularity breaks software into self-contained units (functions, classes, packages) to simplify software development.
As software evolves, complexity increases (Lehman’s Laws). Modular design helps manage this growth.
Refactoring improves internal structure without changing behaviour.
Coupling measures how tightly modules depend on each other. Aim for low coupling (independent modules).
Cohesion measures how focused a module is. Aim for high cohesion (each module does one well-defined task).
Reuse is desirable but must be balanced — it can increase coupling if not applied carefully.
