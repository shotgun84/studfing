7/46
But text editors can undo changes. . .
►Most text editors provide an "Undo" feature, but this is not a reliable 
solution for managing versions. A few reasons:
1.
You often want both the old and new versions.
►Just because something is broken doesn’t mean you should discard 
it.
►You might find a way to fix it later.
2.
The editor’s “undo buﬀer” is only temporary (in general).
►Editors forget all the undo information when you close them.
►If your system crashes, you may lose everything.
3.
There’s still too much for you to remember.
►Since your last working version, you may have edited multiple files.
►Undoing changes across different files is difficult without a proper 
history.

Introduction to Software Engineering - Version Control
Understanding VCS - Local Repository vs. Working Directory
Working Directory
►The working directory is where you create, edit, and delete files.
►It behaves like a normal folder on your computer.
►Usually contains the latest version of your project (but this can vary based on branches).
►Any changes made here are not tracked by the VCS until explicitly saved (committed).
Local Repo
►The local repository stores all previous versions of your project.
►It keeps a complete history of changes.
►In Git, it is stored in a hidden .git/ directory, and in Mercurial, it's .hg/.
►Uncommitted changes in the working directory are NOT saved in the local repository yet.
►Once changes are committed, they are permanently stored in the local repository.
►The repository structure is VCS-specific and cannot be directly read by humans.

How the VCS Manages These Two Areas

►Allows you to restore a previous state of the project if needed.

46/46
►Git automatically merges branches when possible, but conflicts arise 
when overlapping changes occur.
►First, it ﬁnds the “common ancestor”: Identifies the last shared 
commit before the branches diverged.
►Second, Git executes the “diﬀ3” algorithm. This tells it:
►Determines what changed and what remained the same in 
each branch.
►If changes are in different parts of the file, Git merges them 
seamlessly.
►If both branches modify the same section, Git can’t decide which 
version to keep.
►This results in a merge conflict, requiring manual resolution.

50/46
Multiple Repositories – Why?
1. Safety
►In a centralized VCS, if the repo is corrupted or deleted, all data is lost.
►A distributed VCS (e.g., Git) acts as a natural backup.
2. Reliability
►If a centralized server goes down, no one can work, leading to major 
productivity loss.
►With a distributed VCS, developers can keep working locally without 
needing access to the server.
3. Performance.
►Centralized VCS struggles with large teams and heavy network traffic.
►Distributed VCS reduces network dependency and spreads CPU load across 
developer machines.
►Team size doesn’t impact performance since each developer works 
independently.

Remote Repositories in Git
►Each Git repository tracks remotes (external repositories it syncs with).
►Typical Setup:
►“origin” is the central repo everyone syncs with.
►Developers push & pull changes to/from origin.
►Git is ﬂexible, though:
►No central repo: Developers sync directly with each other’s local

►The central repo (if it exists) is mostly for coordination:
►Removes any doubt as to who has the latest version.
►Minimises the amount of syncing needed – you only need to keep 
your local repo in sync with one other (typically).

►This creates a bare repository that cannot be edited directly.
►It is typically used as a central repository that multiple developers 
push/pull from.
►No one works in a bare repo—it only acts as a hub for collaboration.
►Why not just use a normal repository instead?
►A normal repository has a working directory, meaning anyone 
could accidentally edit files directly in the central repo. 
►A bare repository prevents this, enforcing that all changes must 
come through git push and git pull.

Don’t Panic
►Can push and pull overwrite things?
►What if multiple developers push changes at the same time?
►You don’t have to worry!
►git push and git pull never overwrite commits.
►Every commit in Git is immutable (unchangeable)
►New commits are always added, not replaced.
►If two developers try to push different commits at the same 
time, Git prevents conflicts by rejecting one of the pushes.

57/46
Working as a Team
Git can be used in diﬀerent ways, but here’s a reasonable scenario:
1.
The central repo contains a “master” branch.
2.
Developer 1 wants to work on a new feature:
1.
Pull the master branch (so the local repo is up-to-date).
2.
Creates a new feature-X branch in their local repo.
3.
Gets feature-X working, making some commits.
4.
Pushes feature-X (the whole branch) to the central repo. (pull request 
is raised).
3.
Developer 2 performs a code review:
1.
Pull feature-X from the central repo.
2.
Inspects the code.
3.
If anything is wrong, we repeat from step 2.3.
4.
On the central repo, the team now merges feature-X into master.
5.
All developers pull/fetch master from the central repo (so as to be up-to-
date).
